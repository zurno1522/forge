# Choice input context: contract and boundary inventory

Implementation status: the first representative increment is described in [Inline choice input contexts](Simulation-Input-Context.md); [profile V2 adds bounded active-stack inputs](Simulation-Stack-Input-Context.md) and [V3 adds typed controller request constraints](Simulation-Prompt-Input-Context.md). The contract below remains the broader acceptance target.

Status: design and source inventory only. This document does not implement a producer, change the wire format, widen current visibility, or mark data training-ready. Audited source baseline: `cb852fe2ea73fed1a2e5e2eda848eb05dc890afe` on `goldfish-trace`. Source line links refer to that baseline; function and boundary names are the durable inventory keys.

This is stage 1 of the agreed sequence: contract and inventory; representative inline capture; broader coverage and measured optimization. Existing behavior and validation remain documented in [Simulation decision records](Simulation-Decision-Records.md). Existing conservative masks remain unchanged; a richer view in a future capability does not silently declassify old options, result or handler fields. In particular, version 1 deliberately omits opponent hands, library identities and inspected face-down identities. Those are declared limitations, not newly reproduced engine defects.

## 1. Contract decisions

**At an audited input boundary, a context freezes the represented player view, the supplied choice inputs, and information actually disclosed to the relevant recipient. Its timing, perspective, state basis and coverage must describe that boundary accurately.** It is not automatically a complete player information set, complete AI input, Markov state, legal-action mask or strategic explanation.

The following requirements apply to the proposed capability. They are not claims about fields currently emitted.

| ID | Required behavior |
| --- | --- |
| C01: inline ownership | Add an optional, frozen, versioned `inputContext` to the existing owning record. Use the existing decision/choice/application IDs and lifetimes. Do not add an observation stream, observation-ID allocator, gameplay database or observation-reference registry in the first implementation. |
| C02: separate meanings | Keep the permitted player view, original supplied prompt/options, planner working context and returned result distinct. Existing `options`, `priorTargets`, X proposals and operation fields retain their existing meanings; do not duplicate them merely to populate a new container. |
| C03: truthful timing | A snapshot before a callback is preselection input only if the callback actually performs the identified selection. A callback returning an already selected value is not preselection; distinguish cached/result returns from assignment/application. Post-evaluation candidate metadata remains result data. |
| C04: explicit perspective | Resolve the decision subject, current controlling player and visibility perspective at the boundary. Ordinary delegation uses the receiving chooser's permitted view, not the action owner's private state. Unsupported control contexts cannot borrow another player's observation. |
| C05: permission plus disclosure | Base permissions and facts actually delivered to the recipient are separate information sources. Neither option membership, engine `Remembered`, AI memory membership nor a `NoLooking` parameter alone establishes which identities are known. |
| C06: state basis | Distinguish committed rules state at an audited boundary from planning working state. Keep the initial main-phase baseline separate. A fresh engine read during hypothetical evaluation must not be labeled a committed world snapshot. |
| C07: identities and features | Reuse run/game-scoped engine references for diagnostic joins, adding `gameTimestamp` where the new card projection represents an incarnation. Raw engine IDs, timestamps, registry keys and privileged trace columns are not model features or evidence of player-observable continuity. |
| C08: freeze facts | Emit detached scalar JSON values. Never retain a live `Card`, `CardView`, `Game`, ability, controller or mutable option collection in a published context or disclosure fact. Freeze the presented face at delivery; do not reconstruct it later from current hidden state. |
| C09: missing is explicit | Distinguish captured empty data, hidden data, unsupported coverage, unresolved bindings, truncation, exhausted budget, interruption and capture failure. Unknown data must not be filled from a later reveal, outcome, deck manifest or current privileged object lookup. |
| C10: preserve policy | Capture does not invoke/retry a selector, enumerate additional legal actions, sort/mutate its original input, change random calls, restore temporary game state, pay costs or advance execution. The original callback runs once and preserves its result/exception. |
| C11: bounded lifecycle | Bound individual payloads and total context work. Enumerate outside the parent publication monitor; stop on cancellation and recheck admission before publishing. Closing a parent/game prevents late capture from changing it or attaching to another decision. |
| C12: optional compatibility | Absence of the capability on old input means unavailable. Preserve old schema meanings, existing IDs, source order, full/filtered parity and legacy export behavior. Unknown context versions must not silently acquire version-1 semantics. Existing exact-field validators need deliberate optional-capability updates; older consumers may reject new fields and are not promised forward compatibility. |

### 1.1 Semantic envelope

The namespace is `inputContext`; its own `schemaVersion` is independent of existing decision, choice and target-provenance versions. The next stage will define the exact field-level projection profiles and validators. This table fixes their semantics without pretending that a complete card/state feature schema already exists.

| Component | Contract |
| --- | --- |
| Version and capture status | `CAPTURED` means all components promised by the named partial profile were captured. `PARTIAL` identifies missing/truncated promised components. `UNAVAILABLE` carries an explicit reason. None of these means complete Magic knowledge. |
| Timing | `BEFORE_SELECTOR`, `BEFORE_OPERATION`, `AFTER_SELECTION_BEFORE_APPLICATION`, or `UNESTABLISHED`. Name the actual observed function scope. An outer operation's context cannot stand in for a later inner selector. |
| State basis | `RULES_STATE`, `PLANNING_WORKING_STATE`, or `UNESTABLISHED`, supported by the boundary audit. In-progress resolution or partially paid costs can be real rules state; hypothetical face/target/resource tests are planning state. |
| Perspective | Identify the rules chooser and current controlling player where applicable. Reuse existing envelope IDs when their meanings agree and validate consistency. An unresolved information perspective yields unavailable context rather than a guessed union of hands/memories. |
| Coverage | Name the player-view profile/version; stack/resolving coverage; current-prompt/resolution disclosure coverage; and historical-knowledge coverage. The initial profile must explicitly declare long-term knowledge/history incomplete. |
| Player view | Only supported, permitted fields: public/current characteristics and allowed private identity are separate. A stack or currently resolving object is bounded and permission-filtered, or explicitly unavailable; an empty-stack parent is not the template for all callbacks. |
| Choice inputs | Retain the original offered list, range, constraints and supported local arguments in their existing roles. Record dynamic amounts, mandatory/optional request, relevant players and prior selections where those are actual inputs and authorized. Original membership/order stay in their existing diagnostic role. A policy projection must separately authorize membership, count and order; hiding card names alone does not make a hidden-derived pool safe. An observed heuristic pool remains an observed heuristic pool. |
| Disclosed facts | Immutable values actually presented to the observed recipient, with delivery/scope/face provenance and current-object association only when established. A disclosed superset can be larger than the selectable subset. Unsupported or unobserved disclosure coverage is not an empty fact list. |
| Bindings and policy projection | Diagnostic references support exact joins. Any model-facing entity/option references are local to the context initially; the explicit feature projection excludes diagnostic IDs, hidden metadata and future facts. Do not introduce cross-context stable handles before observable continuity is defined. |
| Omissions | Typed component/reason metadata distinguishes `HIDDEN`, `UNSUPPORTED`, `OUTSIDE_CAPTURED_PREFIX`, `UNRESOLVED_BINDING`, `BUDGET_EXHAUSTED`, `INTERRUPTED`, `CAPTURE_FAILED` and `NO_AUDITED_INPUT_BOUNDARY` as applicable. Hidden fields need not expose their private values or reasons derived from those values. |

A result/terminal payload remains separate from its initial context. Do not backfill `selected`, final targets, committed modes, spent resources or outcomes into initial inputs. An accepted operation is not proof of legal alternatives, successful execution or strategic value. Generic standalone `COMPLETED` can accompany `accepted:false`; search-application `DECLINED` has different existing semantics. Context capture status must not reinterpret either.

### 1.2 First supported information model

The target is a **rules-permitted partial view plus the represented prompt and its actual disclosures**, not a dump of every field the existing AI could read. This does not certify that every heuristic uses only the represented inputs.

Ordinary and explicit delegated choices are the first perspective cases. Controlled-player/search-only control and team-sharing behavior require their own permission tests before being marked supported. Until resolved, the context must report unsupported perspective; recording a control-player ID alone does not establish the correct private view. Do not silently merge master, slave or teammate AI memories.

Immediate disclosure support is required in the first representative implementation. Preserve facts needed by subsequent synchronous subabilities in the same observed root-resolution interval, including Intuition's opponent choice. Discard the bounded scope at completion/error and game close. A reusable ability ID or action ancestry is not a resolution lifetime. For direct/nonstack paths without an audited interval, include directly observed current-prompt disclosures and declare prior-resolution coverage unsupported. Do not carry a speculative scope into the next action.

Durable knowledge, hidden-hand inference, historical library tracking, controller-to-controller knowledge transfer and full perfect recall remain separate work. A past fact can remain frozen while its association with a current hidden object becomes unknown. An observable zone/face change, a hidden shuffle or ambiguous private transition must never be bypassed by matching raw IDs or stale memory.

## 2. Architecture, storage and failure boundaries

One AI-owned projection builder should serve the existing parent, standalone, nested target and search adapters. It consumes explicit perspective/prompt/disclosure inputs and returns detached data or explicit unavailable coverage. It is not a rules authority and must not call AI selection logic. The bounded recipient/resolution disclosure buffer retains frozen permitted facts, not separately addressed observations or live engine objects. Context-local diagnostic bindings are inline data; they do not introduce cross-context identity handles.

Use the existing event publication path. [AiChoiceEvent](../../forge-ai/src/main/java/forge/ai/AiChoiceEvent.java#L8) already freezes JSON, [AiChoiceRecorder.observe](../../forge-ai/src/main/java/forge/ai/AiChoiceRecorder.java#L58) captures before its supplied callback, and [SimulationTraceCollector.onAiChoice](../../forge-gui-desktop/src/main/java/forge/view/SimulationTraceCollector.java#L241) forwards that payload. Nested records freeze with the parent. No new rules event, learning identifier in `forge-game`, collector lookup map or long-lived engine-reference cache is justified for this increment.

An optional context failure must be isolated from construction of the base choice/application record: preserve that record where the existing path can still publish it, mark context unavailable and report unexpected observation failures through the existing Game health channel. Ordinary hidden/unsupported/budget omissions are coverage states, not engine errors. Sink or whole-event failure can still prevent publication and remains a visible trace failure; this contract does not guarantee output through failed I/O.

Per-context bounds must cover entities, option bindings, stack/ability groups, disclosure facts and text. A total budget must cover nested decisions and standalone contexts across a game; bounding only each list is insufficient. Exhaustion omits or truncates the context with explicit coverage, not the choice or its callback. Record omission counters so sampling bias is visible. Actual numeric defaults are a measured implementation decision for stage 2, not values silently inherited from the 128/256 target-only limits.

Do not use a global game lock or perform potentially blocking traversal under the recorder publication monitor. Disabled recording and simulation copies do no new projection/disclosure work. Capture itself consumes CPU/allocation and can affect an existing thinking deadline; preserve policy calls but do not promise timing neutrality.

Keep inline snapshots initially. Export-time compression or normalization may follow measurement. Same parent, phase, thread, stack item or engine-event count does not authorize reuse. Equality of fully captured permitted projections, including perspective, coverage, omissions and meaningful order, establishes equality only of represented information, not full engine state or AI memory. Avoid an engine revision/invalidation protocol for this stage.

## 3. Inventory method and classifications

The inventory covers the current production recording entry points, not every Forge choice API. Count call sites from policy/controller code into recording adapters; exclude adapter-internal forwarding, utilities, type declarations and unobserved tokens. At the audited revision there are **61 such sites**: 32 target, 23 mode/numeric/payment and six direct controller-operation wrappers. They use **30 distinct named boundaries**: 13 target, two mode, five numeric, six payment and four controller-operation boundaries. The main baseline/candidate/land metadata and five search-operation variants are listed separately. Masking replacements are projections, not additional selector coverage.

Classification is relative to the stated function, not a blanket training-eligibility flag:

- **S:** before an actual selector or explicitly bounded composite selection; caller inputs may already be heuristic-filtered and the state may be planning state.
- **O:** before a whole preparation, dispatch, revalidation or payment operation; inner selections need their own capture.
- **A:** after selection/computation, before assignment/application; useful causal input for that operation, not preselection input for the earlier policy.
- **R:** cached/returned metadata, final facts or an existing unsupported decline; no fresh selector is established.

All sites remain subject to perspective, disclosure, working-state and coverage checks. `BEFORE_SELECTOR` alone does not make a row a complete training example.

## 6. Next stage and deliberately deferred decisions

Stage 2 should extract the shared partial-view builder and implement optional inline context on a small, audited set of S and O boundaries. Include ordinary/delegated selection, real delayed/chained disclosures and a payment selector, with the gates above. Keep A/R boundaries honestly classified until an earlier seam is instrumented. Do not widen every existing callback in one change.

The following implementation choices remain explicit rather than silently guessed: exact field-level partial-view/stack/disclosure profile; numeric capture budgets; resolution entry/exit coverage for direct/nonstack calls; supported presented-face and current-object bindings; and supported controlled-player permission composition. The contract already defines conservative unavailable/partial behavior for unsupported cases. Resolve each choice with source audit and representative tests before claiming that support; no separate user approval flow is implied.

Broader selector coverage, full historical knowledge/belief state, stable model-facing identity across contexts, full legal sets, per-option search values, reward/training policy and producer-side deduplication remain separate work. All current datasets continue to declare `trainingReady=false`. No benchmark, runtime test or new coverage claim is created by this document alone.
