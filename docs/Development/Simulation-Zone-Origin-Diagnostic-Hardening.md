# COV-006: bound diagnostic zone-origin requests

V8/V9 bounded the permitted origin projection but serialized diagnostic origins with an unbounded stream. A valid engine argument list can exceed the wire's origin limit, including through duplicates. The original callback could finish with healthy observation status while emitting a row the exporter rejected. This is a branch-local instrumentation defect, not an engine/card rule defect.

`AiZoneOrigins` now captures an exact list of at most one enum vocabulary's worth of origins. Preserve order and duplicates. Refuse null values/lists, negative or excessive sizes, iterator/count disagreement and an iterator exceeding the bound. Read at most the bounded number of enum values; an excessive reported size performs no enumeration. Do not truncate and label a request complete. Actual getter Runtime failures retain their observation-failure handling.

A private recorder signal represents a known unsupported metadata shape. Catch it only during options preparation, before publication. Close that observation, classify the existing source scope as `omittedUnsupported`, run the original callback once and preserve its result/exception. The closed observation masks an older diagnostic parent, while the existing exact-admission callback masks/restores the zone-history owner. No terminal/result getters run for that omitted capture. A marker thrown by the original callback remains the original callback exception. Closure wins over late metadata values/faults; no publication monitor surrounds getters. The cap does not preempt a blocked getter.

The existing fixed accounting schema/boundaries represent this omission; there is no new field, profile, engine API or budget. Valid V12 wire output remains unchanged. An unsupported metadata omission is distinct from an unavailable input component in a retained record, from a failing getter and from an engine callback error. Counting the omission does not establish complete decision coverage or learning readiness.

## Validation and review

The targeted reactor passes 133 Java tests, including 18 new origin/admission cases. These exercise both actual adapters, oversized refusal before enumeration/result getters, an unbounded iterator with a misleading size, null/inconsistent lists, exact-limit ordered duplicates, real getter failure visibility, original callback exception identity, the marker outside metadata preparation, four blocked-read closure/late-value cases and nested owner masking/restoration. Existing bypass, receipt/history, actual movement, request and accounting tests pass in the same run.

An isolated baseline compilation of the three affected adapters/recorder from `f1fd099f8c3` reproduces both failures without changing the checkout. Each baseline callback runs once and returns the original result, but emits two lifecycle rows containing 21 origins; the decoder rejects the start. The fixed adapters run those same callbacks once, return the same result, emit no invalid row and count one unsupported omission with zero observation failures. These are explicitly reproduction excerpts, not valid complete-game traces.

Two fresh games complete normally with full/filtered data parity, reconciled source/collector counts, no observation failures and two shuffles before `GAME_STARTED`. Across 886 normal choice starts, options, input context and independent entry data exactly equal the saved V12 games. The ordinary fixture's normalized engine events equal V12. Exporter/Python sources are byte-identical to the tested V12 baseline, whose 223 Python tests and 168-stream legacy comparison remain applicable; no unchanged consumer-suite rerun or new full-reactor result is claimed here.

Review finds no remaining demonstrated current/prior defect in this hardening increment. Spell-ability operation/selector requests are next under COV-006; completeness/knowledge requirements remain COV-004, payment/X COV-007, sustained availability COV-008, and expanded cost/retention OPT-005. The bounded diagnostic helper and known-unsupported admission path belong in the later cost assessment. No optimization or cap increase is bundled here.
